# Firebase 접근 권한 전환 설계

상태: 미구현·미배포. 현재 데이터 보존 수정만으로 보안 문제가 해결되지는 않는다.

## 확인된 현재 구조

- index.html은 익명 로그인을 실행한 뒤 관서 코드를 브라우저에서 비교하고, role을 localStorage에 보관한다.
- 저장소의 firebase-database-rules.json은 익명 사용자를 포함한 auth != null 사용자에게 incidents·archives·config/agencyCodes의 넓은 읽기·쓰기를 허용한다.
- mci와 mci2는 같은 Firebase 프로젝트를 사용하며 경로만 분리한다.
- 실제 Firebase 콘솔에 적용된 규칙이 저장소와 같은지는 미확인이다.
- 따라서 DB 규칙의 auth != null만 갑자기 역할 조건으로 바꾸면 현재 사용자 전체의 조회/입력이 막힐 수 있다.

## 제안하는 전환

1. Firebase의 현재 규칙과 인증 제공자 설정을 읽고 기존 접근 경로를 확인한다. 실제 환자 데이터 조회는 필요하지 않다.
2. mci2를 별도 Firebase 테스트 프로젝트로 분리한다. 경로만 분리한 상태는 보안 경계가 아니다.
3. 사용자를 신뢰할 수 있는 서버에서 확인하고, 관서 ID·역할·환경을 Firebase 인증 토큰에 부여한다. 클라이언트가 보낸 role이나 localStorage 세션은 권한 근거로 쓰지 않는다.
4. 기존의 빠른 관서 진입 UX가 필요하면 서버가 검증하는 관서별 발급 코드로 바꾼다. 공개 소스에 있던 코드/관리자 코드를 인증 비밀로 재사용하지 않는다. 코드 목록은 로그인 전 사용자에게 전송하지 않는다.
5. 단말/사용자 식별 UID를 보존하고 필드 작성자/수정자 권한을 UID로 검사한다. 이름 문자열 비교로 소유권을 결정하지 않는다.
6. 관리자만 권한·관서 코드를 관리한다. 읽기 전용 역할의 모든 쓰기와 다른 관서 재난에 대한 접근을 DB 규칙에서 거부한다.
7. 현재 incidents/·archives/ 전체 구독을 권한에 맞는 인덱스/쿼리로 바꾼다. 환자 사진·상세 기록은 선택한 사건에서만 요청한다. 규칙은 데이터 필터가 아니므로 상위 전체 읽기를 열어 해결하지 않는다.
8. 인증·쿼리·규칙·OCR API 권한 검사를 한 묶음으로 mci2에서 검증한 뒤 운영으로 전환한다. 운영 권한 강화 시 오래된 앱과 오프라인 미전송 기록의 처리도 결정한다.

## 권한 검증 기준

| 주체 | 허용 | 거부 |
|---|---|---|
| 미로그인 / 미승인 익명 사용자 | 로그인 절차 | 환자/재난/관서 코드 읽기·쓰기 |
| 일반 관서 사용자 | 소속 관서 재난의 허용된 업무 | 타 관서 접근, 관리자 설정, 권한 승격 |
| 관찰자 / 표출 | 승인된 범위의 요약 조회 | 환자 수정·삭제, 코드 변경 |
| 관리자 | 승인된 환경의 관리 기능 | 테스트 자격으로 운영 접근 |
| 현장대원 | 본인 UID로 생성한 카드의 허용된 수정 | 작성자명 위조로 다른 카드 수정 |

추가로 토큰 만료·로그아웃·권한 회수·오프라인 재전송·팝아웃 창·재난 종료 후 쓰기를 검증한다.
Firebase Emulator에서 먼저 거부/허용 테스트를 하고, 그 다음 mci2에서 역할별 두 단말 검증을 한다.

## 필요한 연결

GitHub 연결만으로 Firebase 콘솔의 실제 인증 설정/규칙 배포나 Cloudflare Worker의 배포 연결을 변경할 수는 없다.
Cloudflare와 Firebase에 대한 인증된 접근이 확보되어야 기존 설정을 확인하고 배포·마이그레이션을 완료할 수 있다.
비밀키를 대화나 GitHub에 붙여넣지 않고 서비스의 인증/Secret 설정을 사용한다.
